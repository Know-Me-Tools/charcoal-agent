# 1.5 Integration gate: saved-chats reset notice (app-db-reset-notice)

Status: PASSED in Chromium against the built app. Not run in WebKit or Firefox; not run against the live site or a real UAR.

## Method (task 1.1)

A damaged IndexedDB does not reach the path. The only message `DbProvider` matches ("bundle size") comes from `@electric-sql/pglite` 0.3.15, `getPreloadedPackage`: `Invalid FS bundle size: ${fetched.byteLength} !== ${expected}`. It checks the size of the fetched `pglite.data` asset, not stored data. In production this is a stale cached asset after a deploy.

The honest reach is therefore at the network boundary: Playwright serves a 1 KiB body for the first `pglite.data` request and passes later ones through. The real library throws, the real `DbProvider` purges `/pglite/charcoal-db` and reopens, the real app renders. Nothing in the app is mocked. The UAR backend is the suite's usual Playwright mock.

Limit: this proves the reset path and its notice. It does not prove that a corrupted IndexedDB triggers it (no such state was found to throw this message).

## Run

- Build: `vite build` exit 0 (dist/ not committed).
- Serve: `vite preview --port 4392`.
- Spec: `e2e/db-reset-notice.spec.ts`, run with `E2E_PORT=4392 E2E_REUSE_SERVER=1`, Chromium project, one worker, no retries.

Result: `2 passed (48.3s)`
- `a normal start shows no reset notice`
- `a database that cannot be opened is reset once, with one notice, and the next load is quiet`: creates a saved thread ("Weekly plan") through the real composer, reloads to prove it is stored, serves the bad `pglite.data` once, reloads, then asserts: exactly one notice element, `pglite.data` requested exactly twice (one bad open, one reopen), the thread is gone from the sidebar; removes the fault, reloads, asserts no notice and an empty list.

The same spec also passed against the dev server (`2 passed (1.3m)`).
