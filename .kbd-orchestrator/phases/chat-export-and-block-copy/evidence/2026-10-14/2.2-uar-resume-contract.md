## The contract (at 2cc9a182; headers confirmed at 3e6af7c4)

- Resume is the **same POST** as a chat turn (`/api/chat/completion`), not a separate GET.
- Request headers `x-uar-run-id` and `Last-Event-ID` must be sent **together**, with `stream=true`. One without the other, or with `stream=false`: 400 `invalid_replay_request`. A cursor that does not parse: 400 `invalid_replay_cursor`.
- Cursor grammar: `<event_id>` or `<event_id>:<frame>:<format>`; format 0 openai, 1 agui, 2 dual, 3 agui_spec. A different format from the request's `stream_mode`: 400 `replay_format_mismatch`. The site proxy pins `stream_mode: "dual"`, so its cursors are format 2.
- Every projected frame carries `id: <source_event_id>:<frame_ordinal>:<format>` (for example `id: 17:0:2`), including `[DONE]`. Keep-alives go out every 15 s.
- Response headers include `x-uar-run-id` and `x-uar-session-id`.
- Ownership: the run must exist and belong to the verified owner (404 `run_not_found` otherwise). The owner is the **proxy's credential identity, shared by all visitors**, so it does not separate visitors. The real cross-visitor guard is the session id: an `x-uar-session-id` that differs from the original run's session returns 400 `replay_session_mismatch`; if the header is absent the check is skipped. The site proxy always sends its derived per-visitor session header.
- A resume does not parse or use the body, forces memory off, and starts no new execution.
- Buffer and retention: in-memory ring of 512 events per run; terminal runs kept 600 s (up to 1000). A run with more than 512 events, or one past retention, cannot be resumed: 410 `replay_history_expired` or 404. A cursor at the terminal frame returns an empty success; resuming a finished run within retention replays the remaining frames including `[DONE]`.
- Disconnects: a 250 ms grace after the last subscriber drops cancels the run. Whether a browser reconnect inside that window reattaches in time was **not traced**.
- UAR integration tests cover reconnect, wrong format, bad cursor, missing cursor, terminal cursor and expired history (`tests/integration/live/chat_replay_cases.rs`).

## What this repo does today (read at origin/main)

- `site_proxy.rs` lines 10 to 12: resume is not forwarded. `forwarding.rs` allowlists only `content-type` and `accept` as request headers (so `last-event-id` and `x-uar-run-id` are stripped; a test asserts it) and only `content-type` and `cache-control` as response headers (so the browser never learns the run id).
- `agui_filter.rs` parses only `event:` and `data:`, drops upstream `id:` lines and rebuilds every frame without an `id:`. The client therefore has neither a run id nor a cursor.
- `chat` always calls `meter.admit()` and creates a turn tracker; a resume has no path that skips it.

## What forwarding resume would need (analysis, not confirmed in code)

1. A run id the client can use **without being able to name another visitor's run**: a server-side token (bound to visitor, thread and run id, with a TTL) instead of exposing the raw UAR run id.
2. `id:` lines re-emitted by the filter, with a cursor that stays consistent where one upstream event becomes several filtered frames or derived frames (`agui.step`, `agui.web_citations`).
3. A resume request that sends both headers together with `stream=true`, validates the cursor locally (`^\d+(:\d+:\d+)?$`, format 2), and still passes the proxy's body builder.
4. A metering path that **does not admit or reserve again** and does not settle on replayed `agui.done` usage; the original tracker settles as `Disconnected` on drop, so a resume cannot reuse its reservation. Not traced.
5. A client fallback for 404 and 410 (start a new turn, or show the stored partial transcript).
6. Verify the 250 ms disconnect-cancel grace against a real browser reconnect.

## Consequence for the plan

Change 2 (`site-stream-resume`) is a medium-to-large server change with a security surface (run-id token, replay of another visitor's run), a metering change, and a UAR behaviour (10-minute window, 512-event limit) that bounds what it can fix: a phone locked for longer than the retention, or a very long reply, still cannot resume. The decision gate (task 2.1) should weigh that bound against what task 1.1's logs and the real-iPhone run (1.8) show.
