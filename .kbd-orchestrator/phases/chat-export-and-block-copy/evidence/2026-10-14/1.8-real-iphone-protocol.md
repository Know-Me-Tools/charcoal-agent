# 1.8: real-iPhone protocol (operator runs it; results go in `1.8-real-iphone-results.md` in a new dated folder)

Why this exists: Playwright WebKit on a Mac is not iOS Safari and has no thermal signal. The tasks in this change bound the work the page does per token and measure proxies, but only a real iPhone can say whether the phone stays cool and whether replies finish. Heat stays **unverified** until this protocol has been run and its results recorded.

## What you need

- An iPhone you have seen get hot and lose replies, with iOS version and model written down.
- A Mac with a cable, for Safari Web Inspector (iPhone: Settings, Safari, Advanced, Web Inspector on; Mac Safari: Develop menu, your iPhone, the know-me.tools tab). The code from task 1.1 writes failures to the **console only** (no telemetry, by design), so without Web Inspector the diagnostic is invisible. If you have no Mac, skip the console parts and record behaviour only; say so in the results.
- Low Power Mode **off** (iOS throttles animation and timers in Low Power Mode and would hide the problem), battery above 50 percent, unplugged, screen auto-lock set to 30 seconds for the lock test and restored afterwards, Safari tab open on https://know-me.tools (a normal tab, not a home-screen app).

## Two runs

Run the whole protocol **twice**: once on the site as deployed now (the baseline, before change 1 ships) and once after change 1 is merged and deployed. Same phone, same Wi-Fi, same prompts. Record which deploy each run used (the `Deploy site` run id).

## Steps

1. **Cold start.** Close the tab, reopen the site. Note how long the page takes to become usable and whether the phone warms up while it loads.
2. **Long reply, screen on (the heat test).** Start a new thread. Send a prompt that produces a long answer with code, for example: "Explain in detail how The Boss differs from a plain chat client, with three code examples." Keep the screen on and the page in the foreground for the whole reply and one minute after. Record:
   - did the reply finish (yes or no), and how long it took;
   - how warm the phone felt on a 0 to 3 scale (0 cool, 1 slightly warm, 2 warm, 3 uncomfortably hot), at the start, at the end of the reply, and after one more minute;
   - battery percent at the start and after five minutes of this;
   - if Web Inspector is attached: a Timelines recording (CPU and JavaScript and Layout) of the reply, saved as a file.
3. **Lock test (the lost-reply test).** Send the same prompt. Three seconds after sending, press the side button to lock the phone. Wait 20 seconds. Unlock. Record whether the reply finished, partly finished, or shows "The reply stopped before it finished"; and, if Web Inspector is attached after unlock, the console line with `event: "stream-failure"` (copy errorName, errorMessage, visibilityState, elapsedMs, receivedBytes; it contains no message text).
4. **App switch test.** Send the prompt, switch to another app for 20 seconds, come back. Same record as step 3.
5. **Repeat step 2 once** with a different long prompt, to see whether the first result was a fluke.

## How the results are used

- If the lock and app-switch tests fail with `visibilityState: "hidden"` and an `errorName` such as `TypeError` (typically "Load failed"), cause 1 in the plan (iOS kills the connection) is confirmed, and task 2.1 can approve `site-stream-resume`. If the stream dies with the page visible, the cause is elsewhere (task 2.1 cancels the resume change).
- If a failure shows elapsed time near 300 seconds, the route's 300-second cap is the cause (a separate, small fix).
- If the phone stays warm after change 1 in step 2 with no failure, the per-token work is not the whole story and the Timelines recording says what is; that becomes a new task in this change, not a silent pass.
- Passing this protocol does not prove heat is solved for every phone; it records one device, one network, one day.

## Result after PR #125 (2026-10-17)

Operator report, in chat, after PR #125 (server keep-alive every 10 s, page stall watchdog at 45 s) was live in production: "it works!"

- Prompt: "Explain in detail how The Boss differs from a plain chat client, with three code examples." This is the prompt that stalled on the iPhone 17 and the iPhone 18 (web search on) before the fix.
- Recorded: the operator reports the reply now completes. Not recorded: device and run details, finish time, heat reading, battery delta, lock test, app-switch test. The operator gave a one-line verdict only.
- Server side, measured from a Mac against production after deploy 39055320125: keep-alive frames at 13.9 s and 31.8 s, no gap over 12 s, 46.9 s total, ends with `agui.done`. Before the fix the same prompt had silent gaps of 29 s and 18 s.
- Not proven: that silent connections were the whole cause of the heat. The lock and app-switch steps of the protocol were not run, so resume after backgrounding is untested on a phone.
